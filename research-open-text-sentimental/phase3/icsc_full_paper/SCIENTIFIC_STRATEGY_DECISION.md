# Scientific strategy for the ICSC regular paper

**Date:** 2026-10-08. **Purpose:** choose the highest-value next research work without restarting, collecting an entirely new corpus, or writing the manuscript. This is a recommendation, not a new empirical result. The saved Phase 1–3 datasets and test results are unchanged.

## The research question worth remembering

The 2024 Singh/Berhe paper asks whether Reddit feedback enriches release notes and helps prioritize high-impact updates. Our defensible additional question is **what information must a social-media update discussion contain before it becomes useful evidence for software investigation?** That has at least three separate parts:

1. **Connection:** Is the post actually about a software update? The current experiment uses human scope decisions.
2. **Purpose:** Is the author trying to diagnose, report, or solve a concrete malfunction, rather than discussing an update for another reason? This is the tested classifier task.
3. **Evidence:** Does the saved post provide enough context for an engineer to take a next investigation step? We currently count fields but have **not** validated this judgment.

The scientific proposition is that *purpose and investigation readiness are distinct*. A help-seeking post might lack version, environment, reproduction context, or error evidence; a non-help-seeking account might contain specific incident facts. We have evidence of missing fields among 237 reviewed troubleshooting posts (release detail 122, reproduction context 108, error evidence 40), but no cross-class field study or independent engineer-readiness outcome. Therefore the proposition is a **hypothesis to test**, not a result to write into an abstract now. The observed title-only associations and 46 fresh errors suggest informative boundary cases, but those too are exploratory.

If a focused follow-up confirms this distinction, the paper can become a study of **semantic triage from discussion purpose to usable diagnostic evidence**, not simply a classifier benchmark. “Semantic” here means a clearly defined representation and evaluation of meaning in the post; it does not mean that we invented a semantic architecture or that MiniLM outperformed TF-IDF.

## Why these outrank common alternatives

- **Another transformer or more hyperparameter search:** The frozen MiniLM comparison on 2,136 development posts gained only +0.0059 macro-F1 over TF-IDF with a paired interval crossing zero; it was not tested on fresh posts. Model shopping would add little to the scientific question and risks overfitting the narrative.
- **More bulk labels from the same API pools:** The 3,362-record corpus is already large enough for this bounded question. More similarly selected candidate posts do not resolve whether troubleshooting predictions help a user.
- **An elaborate knowledge graph or ontology:** The current study has no validated entities, relations, or downstream use for one. A diagram of existing labels could clarify the paper; calling it a new semantic system would overstate the work.
- **Sentiment, clustering, or resolution analysis:** These change the target and would fragment an eight-page paper. The Phase 1 sentiment claims are not a reliable central foundation; clustering/resolution have not been evaluated.
- **Claiming an extension of the 2024 release-note system:** The present study uses the same ReleaseTrain platform but a distinct 2025–2026 corpus and different outcomes. Without testing a connection to release-note decisions, call it a related post-level study, not an experimentally validated system extension. See `BERHE_2024_DIRECT_COMPARISON.md`.

## One-study design, if authors choose the strongest path

**Population:** the already frozen 344 S2 fresh-test posts, not a new collection. The existing model and test labels stay locked. This sample is candidate-pool selected and 277/344 are troubleshooting; the result applies only to that setting. If the same posts are used for a new outcome, predeclare this as a new, retrospective outcome study, not a second independent test of the old classifier.

**Blind task:** Two engineers familiar with software issue triage each see saved title/body, with model score, Phase 2 label, source pool, and the other person's answer hidden. They answer separately: (a) concrete malfunction/issue described? (b) enough evidence to start a useful investigation? (c) which missing facts would they request first? (d) confidence. Supply a named hypothetical role (maintainer of the affected product) and say not to look up live Reddit. Pilot the rubric on cases outside the 344, revise once, then freeze it.

**Primary outcome:** fraction of posts judged investigation-ready under an adjudicated rubric, with initial inter-rater agreement reported. Primary comparisons should be prespecified, e.g. investigation-ready yield among posts flagged by the existing classifier versus a fixed keyword rule and an unranked S2 queue at equal review budgets; report precision-at-k/coverage with uncertainty. A majority or chronological queue may be a useful operational baseline only if its ordering is defined independently of outcomes. The model's existing troubleshooting test score is separate from this new utility outcome.

**Secondary analysis:** cross-tab human troubleshooting purpose with investigation readiness; describe which diagnostic fields tend to be absent in non-ready posts. Test associations with text availability and source pool as descriptive, not causal. If field labels are added to the 344, coders should not see model predictions or readiness decisions while coding them. Do not call a simple count of eight fields a validated quality score.

**Stop rule:** If engineers cannot agree on readiness, report that construct as unstable and do not use it as a headline contribution. If ready-post yield is similar across queues, report that troubleshooting detection alone does not improve this offline decision and reconsider the paper's practical claim. Do not tune the existing classifier or threshold on these ratings and present the same sample as an untouched confirmatory test.

## Positioning and PI decision

The best primary frame is **empirical semantic triage for software-update discussions, with a software-engineering decision outcome**. It is not primarily a machine-learning architecture paper. The memorable result should be about the relationship among update connection, troubleshooting purpose, diagnostic evidence, and what an engineer can do next. That is distinct from Singh et al. (2024), which enriches release notes to prioritize update impact. The model is a tool for testing the triage question, not the main invention.

**If this were my paper:** I would first lock this question and study design with the coauthors; confirm data-use permissions and authorship; run the blinded utility study on existing posts; complete the bounded failure review; then decide whether the new results justify an ICSC regular-paper claim. If the utility outcome is weak or irreproducible, I would write the narrower empirical paper honestly and consider a software-engineering venue rather than add decorative semantic terminology. No manuscript writing or new experiment was performed in this strategy task.
